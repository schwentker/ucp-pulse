# CODEX review 1: ucp-pulse

Reviewed 2026-11-04 against [PLAN.md](/Users/andres/dev/ucp-pulse/PLAN.md). This is a findings report, not an implementation or rewritten plan. Primary repository files, release metadata, vendor posts, and local Flight Recorder artifacts were inspected. Mutable pages are observations at review time; cached web results cannot establish an exact historical count. UCP main-branch files below are pinned to 58c7ab9; the August overview is pinned separately. Local trace/fixture citations refer to `ucp-flight-recorder@7ba19c5f6d7b32581486b7cd723ea3aaf71d5b0a` and their linked repository-relative paths; FIELD-NOTES is a modified working-copy narrative. No new merchant calls were made.

## 1. Verdict

**needs rework**

The core product is useful, but the publication boundary, event identity, reporting windows, and compatibility classifications do not yet support its guarantees. Most historical facts are reproducible, but several conflate original releases with later amendments or overstate what the evidence establishes.

| §11.10: Closing watchlist and pending-breaking list | could not verify | This is proposed editorial content, not a supplied list to fact-check. Derive it from stored open notices/PRs plus merged-but-unreleased changes; merged main changes are not pending PRs. |

## 4. Minimum viable v1

1. Resolve the publication boundary. Keep preparation local/private until approved if the owner's literal requirement stands. Publish the source code openly and budget any private Actions runs within free allowances.
2. Define event/revision identity, immutable supporting evidence, UTC periods, per-source cursors, source health and report lifecycle. Implement only the small JSONL store and rebuildable index needed to preserve these invariants.
3. Collect official spec releases, tags, maintained release-branch changes, merged/open breaking PRs, announcements and the two SDKs' package metadata. Verify registry bindings and Discussions access before enabling those collectors. Backfill exact revisions for the corrected history issue.
4. Render a deterministic, source-offline version board and all declared/reviewed breaking changes, with released versus draft/backported status, migration impact and explicit coverage gaps. Begin with changed-path alerts and human schema review; avoid promising exhaustive semantic detection.
5. Prove duplicate dispatch, missed-run recovery, atomic state commits and end-to-end KEEP/CUT publication. Review the first history issue and weekly brief manually, then enable daily collection and weekly draft generation. Seven quiet days alone are not an acceptance test.
6. Publish the approved Markdown/JSON first. Add the existing Hugo presentation only after the review path works. Add narrowly scoped schema rules later; defer the probe, Tier 2, broad blog aggregation, generalized scoring and LLM prose.

## 5. Open questions for the owner

1. **Must drafts and evidence remain private until approval, or only the branded brief?** Recommended: honor the literal private-until-approved requirement; use local/private preparation and a separate public export.
2. **Is v1 a declared-change tracker or a guarantee to find every breaking change?** Recommended: declared plus human-reviewed changes, with coverage labels. Exhaustive semantic detection is not a credible v1 promise.
3. **What identifies a release when its contents change?** Recommended: date channel plus immutable commit/artifact revision, with backports shown under that existing channel.
4. **Should the Shopify probe ship in v1?** Recommended: no. Establish terms, permitted purpose and a meaningful operation-specific comparison before enabling it.
5. **When should the LLM be enabled?** Recommended: only after four reviewed deterministic briefs demonstrate a prose bottleneck and the claim-binding checks pass.
